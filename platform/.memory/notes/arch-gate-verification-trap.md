**Resolved 2026-09-20 (PR #475, commit "Make the per-project CI gates judge
the repository, not the runner").** `pf.architecture._count` now reads the
git index (tracked or staged files only) and the context card and Dagster
registration are `build_output` rows rendered as `⟳` regardless of disk, so a
developer checkout and a runner render the same map. Verified in a clean
clone: all three commodity maps pass `pf arch --check` after `pf kg build`.
The remaining honest caveat: run `git add` before `pf arch`, because untracked
files no longer count. The impact-gate job also changed: it restores only
`groups/<group>` from the base and keeps the PR's `platform/`, and a breaking
radius passes when the PR adds or edits a `decisions/*.md`.

`kg/architecture.md` is rendered by two independent CI pipelines that disagree:
`converged` (platform.yml) runs `pf bootstrap --all` then compares byte-for-byte,
while each project's `architecture` job runs `pf kg build` then `pf arch --check`.
They render the context card, the Dagster registration row and the
capability-doc count differently, so a map written by one is stale to the other
and no committed content passes both. Adding `pf kg build` to `converged` does
not fix it: metrics and dimensions come from `target/semantic_manifest.json`,
which only a real dbt build writes.

**Why:** on 2026-09-20 a local `pf arch --all --check` reported 9/9 ok on
bootstrap-written maps, so they were committed — and CI failed all nine. The
check passes only because `pf bootstrap` writes the state `pf arch` then reads;
running them in that order makes both agree with themselves.
**How to apply:** `pf arch --check` compares a render against the committed
file, so locally it compares your render with your render — it reports 9/9 for
whatever you just wrote, with or without a preceding bootstrap. A clean clone on
this machine is *also* not the runner: it builds a graph with no Metric or
Dimension nodes (`target/semantic_manifest.json` is written by `dbt parse` on
the runner), `git clone --shared` carries no submodules, and a stale `.venv` can
differ from `uv.lock` until `uv sync --frozen`. So do not commit a render of
these files at all — read the diff the failing CI job prints and match that, or
leave the file alone. Committing a locally-rendered map replaced correct files
with guesses three times across two sessions on 2026-09-20. Related traps: `pf bootstrap` deletes
`transform/tests/expectations/*.sql` in a bare checkout — they carry a
`GENERATED by pf bootstrap` banner but each is a live row-count assertion, and
`gate.yaml` omits `D` from its diff filter so nothing blocks the deletion. And
`pf bootstrap` cannot run in a git worktree at all: `install_hook` does
`target.parent.mkdir` on `.git/hooks`, which is a file there. See
[[concurrent-sessions-revert-tree]].
