Commodity Desks, End to End

One monorepo runs many companies at once. The infrastructure is shared, the business logic never is. This follows a single price from a public API to a dashboard, through the Commodity Desks family, and names the rule that applies at every hop.

The idea in one minute

Three tiers, and one prohibition

Everything in the repository sits in one of three tiers. The platform is the machinery, written once. A group is a family of companies that share a vocabulary. A project is one company, with its own warehouse and its own numbers.

The prohibition is what makes it safe: a project may never read another project. Business logic does not transfer between companies, so an assumption carried across is a bug, not a shortcut. Everything else in the design exists to make that rule survive contact with real work.

Crossing the boundary

The one sister allowed to look sideways

Sooner or later someone asks which market is cheapest. That question cannot be answered inside a market, and the answer is not to relax the rule. It is a fourth kind of thing: a roll-up project whose only job is comparison, and which reaches its sisters through a read-only attachment to their warehouse files rather than by reading their code.

That refusal is the load-bearing part. A comparison across markets is only meaningful if every market computed its landed price the same way, so the roll-up is also the test. Adding a market is therefore a small act: one row in the markets seed, its own duty and unit seeds under conformed names, and a warehouse. The catalogue, the units and the connectors already belong to the family.

Knowledge the code cannot hold

Five rules that outrank any request

Every family keeps a short list of things that are true about its business and invisible in its schema. These are the Commodity Desks' own, and they are written where an agent or a new engineer reads them before starting.

  • A price is not additive. It is a unit price, never a money amount. A mean is a sum divided by a count, within one commodity, and never across commodities or markets.
  • Convert in order. Minor-unit quotes first, then units of measure, then foreign exchange. Any other order is quietly wrong.
  • A sister is a market. One currency, one customs regime, one warehouse. If something needs two, it needs two sisters.
  • The conformed core is identical everywhere. Change it in every sister or in none, and let the roll-up prove it.
  • Extraction never transforms. Landing raw and shaping data are different jobs owned by different tools.

Around the pipeline

What the platform adds that a dbt project does not have

The data flow above would work in any warehouse. What makes this a platform is the layer around it: a vocabulary the models are checked against, a graph that answers questions instead of being read, gates that block a merge, and a record of what every agent did.

Loops

tools.yaml		 A capability that also runs: one declaration brings scaffolded files, gate rules, pipeline assets and a UI. Enabled for the family, overridable per market. Deciding the same thing three times, once per sister.

Two of these are worth dwelling on. The graph is asked, not read, which is why a session can reason about a warehouse it has never opened. And the generated artefacts are committed on purpose, so that a pull request shows the change and its consequences side by side. The rule that follows from that is short: change the generator, never the generated file.

A change, end to end

What happens when you touch the landed price

Suppose the duty calculation in fct_landed_prices_daily is wrong. That model is conformed, so it exists identically in every sister and feeds the roll-up. Here is the whole path from edit to dashboard.

  1. Before the edit, ask the graph. The blast radius names the downstream models, metrics and dashboard pages, so the size of the change is known before it is made rather than after.
  2. The gate checks the path. A session working in one market may not write to the platform, to another market, or to the provenance record. A model change also requires its impact to be reported first.
  3. The edit lands in every sister. Conformed means identical. Changing one is the failure the roll-up is built to catch.
  4. The commit is small. At most twelve files, a subject line saying what changed and a body saying why. Larger work becomes a sequence.
  5. Continuous integration rebuilds the derived truth. The knowledge graph, the architecture map and the semantic manifest are regenerated and compared against what was committed.
  6. The review shows data, not just code. The diff between the old and new numbers is computed and posted, because the meaningful question is what the values did, not what the SQL says.
  7. The dashboards are reached through exposures. Each page is a node in the graph, so the pull request can name who to tell.
  8. The action is recorded. Whoever did it, agent or person, and in which order, hash-chained into a ledger nobody in the loop may rewrite.

Who else works here

The repository as something agents can be trusted in

The unusual part of this codebase is that it is written to be operated by more than one kind of worker. People, a chat session with a shell, an autonomous job answering an issue, and an editor completing a line are all held to the same rules, and the rules go by what the worker can do rather than by which vendor built it.

Three files carry that. A short router names the tiers and the prohibitions, and is capped so small that every session can afford to load it. A protocol spells out the scopes, where each may write, which files are generated and what to run before pushing. And a per-module memory keeps the traps that already cost someone a day, in the directory they are true of, indexed and checked so a lesson cannot land without being findable.

The graphs serve the same purpose from the other side. One answers questions about the data. A second, scoped deliberately to the platform directory alone, answers which function calls which. Neither is ever read in full, and asking the wrong one returns a confident answer to a different question.
