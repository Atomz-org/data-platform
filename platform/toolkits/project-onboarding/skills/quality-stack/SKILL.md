# The quality stack

**Goal:** every dbt project in this platform answers three questions with
evidence, not vibes — *did my change move the numbers* (recce), *does the data
hold what the ontology asserts* (dbt-expectations), *what has been true over
time* (elementary). All three are pluggable tools: one `tools.yaml` decision
per family, everything else derived. Your job is never to wire them by hand —
it is to make one declaration and then verify the derivation happened.

## Instructions

**A new group or project needs nothing.** All three tools are
`default_enabled`: `pf new-group` writes them into the family's `tools.yaml`,
and `pf new-project` bootstraps them — packages declared, configs inserted,
docs and permissions applied, gate rules merged. Do not add packages.yml
entries or elementary configs by hand; if they are missing, the fix is
`pf bootstrap <group> <project>`, which retrofits any project to the current
platform.

**An adopted or older project gets one command per tool:**

```bash
pf tool list <group> <project>        # what is on, and where it came from
pf tool enable recce <group>          # group-wide: every sister inherits
pf tool enable expectations <group>
pf tool enable elementary <group>
```

Enable at the *group* unless one entity genuinely differs — a per-project
`enabled: false` is the escape hatch, not the default posture.

**Per-family dials live in `tools.yaml` config, never in code:**

```yaml
tools:
  elementary:
    enabled: true
    config: {schema: elementary, version: [">=0.25.0", "<0.26.0"]}
  expectations:
    enabled: true
    config: {floor: true}     # false = vocabulary only, no generated tests
```

## The loop

Declaration is not proof. Run the derivation chain and check each link:

```bash
pf seed <group> <project>                      # 1. deps install + build; elementary records it
pf kg build <group> <project>                  # 2. graph learns the models and roles
pf tool expectations config <group> <project>  # 3. floor derived from the roles
pf tool recce baseline <group> <project>       # 4. green build captured for diffing
pf tool expectations run <group> <project>     # 5. floor passes
pf tool doctor <group> <project>               # 6. every row ready or explained
```

Then confirm the recording is real — this is the step everyone skips:

```bash
pf loop run observability-triage <group> <project>   # reads elementary history
```

`noop` on a healthy project is the pass; `elementary tables missing` means
step 1 never ran. The ongoing loops (`pf loop list`) keep it true after you
leave: `observability-triage` triages the history on cadence, and
`expectations-refresher` regenerates the floor when annotations move.

## Verification checklist

| claim | proof |
|---|---|
| packages declared | `transform/packages.yml` names all three ranges |
| recording live | `main_elementary` exists in dev; `<schema>_elementary` on the prod engine — every target records |
| edr target-aware | the `elementary:` profile block mirrors every project target (derived; regenerated by bootstrap) |
| floor derived | `transform/tests/expectations/*.sql` match the annotated marts |
| review possible | `transform/target-base/manifest.json` exists |
| governed | `pf air coverage` shows AIR-DET-4 / AIR-PREV-6 enforced |

The stack is engine-agnostic by construction: proven green end-to-end on
DuckDB, DuckLake and Postgres; Snowflake, BigQuery and Redshift use the same
derived profiles and natively supported packages. ClickHouse carries one
honest caveat (see its warehouse docs): date-windowed dbt-expectations may
error there; the generated floor is dialect-safe.

## Rules

- **Never hand-write what bootstrap derives.** A missing declaration means
  bootstrap did not run, not that you should type it. The generated floor,
  `recce.yml`, and the elementary blocks are all regenerated artefacts.
- **Coverage is annotation.** A mart with no generated expectations and no
  recce value checks is an *unannotated* mart — fix
  `contracts/annotations.yaml`, then re-derive. That one edit updates tests,
  review checks and monitors together.
- Judgements stay human: anomaly monitors (`elementary-observe:
  add-anomaly-tests`) and sharper expectations go in the model's own yml.
- Version bumps are deliberate: the ranges pin minors because Elementary's CLI
  and package move in step and its models migrate between minors. Bump in
  `tools.yaml` config (or the tool module's default), never by editing a
  project's packages.yml against the range.
