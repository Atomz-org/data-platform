MCX Platform Blueprint

End-to-end architecture of the MCX commodity pipeline on the data platform: market data from MCX, Yahoo Finance and gold-api lands through dlt, is modelled by dbt in DuckDB, measured by MetricFlow and a Wren semantic layer, served by Evidence and Ask the data, catalogued in OpenMetadata, orchestrated by Dagster and governed end to end. The data diagrams are generated from the project's own artefacts: kg/graph.json, mdl/mdl.json and the compiled dbt SQL.

Preliminary · Architecture principles

The rules the architecture holds itself to

Each principle is enforced somewhere in code or CI, named in the right column.

Principles

8 principles

PrincipleStatementEnforced by
Business logic does not cross entitiesEach project has its own warehouse, dlt, dbt and graph; only the rollup reads sisters, READ_ONLY.Never read another group or sister project.
dlt lands raw, dbt owns meaningNo transformation in a dlt resource; staging never joins.ADR-0004
Prices are unit_price, not moneyPrices are non-additive; means are ratio metrics within one commodity.ADR-0002, ADR-0003
Joins come from the ontologyA realises edge binds a physical FK to a named relation; MDL join conditions are derived, not guessed.projections/mdl.py
Generated files come from generatorsDocs, indexes, MDL, pages and cards are regenerated, never hand-edited.pre-commit gate
Agent actions are recordedIntent, decision and execution are chained and anchored; agents cannot edit the record.docs/GOVERNANCE.md
Controls are named, not assertedEach control carries a FINOS AIR id; coverage is derived at check time.docs/AIR.md
Rerun anything, converge the sameEvery Dagster step is idempotent; dlt resumes from cursors.defs/mcx.py

Phase D · Technology architecture

Where it runs

The shared stack runs in one container behind nginx, with Postgres and Elasticsearch as their own stateful containers. Local development runs dagster dev on :3070 against SQLite and the per-project DuckDB files.

Phases E and F · Orchestration and runs

One job per commodity, one catalogue pass after

Each MCX commodity has a schedule and a job. Every step is idempotent, so any commodity can be rerun at any time; concurrent runs queue on the warehouse writer pool instead of colliding.

Phase G · Implementation governance

Controls on change and at runtime

Change is gated at commit and in CI. At runtime, agent actions are chained and anchored, and each AI control carries a FINOS AIR id that pf air gate checks against the project's commitments.
