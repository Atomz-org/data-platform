# Parallel run: this platform's hand-built knowledge systems vs. OKF

Everything under `okf/bundles/` in this folder is real converted data from
this repository — not synthetic fixtures — run through the actual `okf`
binary (built from `github.com/Atomz-org/okf`, commit at build time recorded
in `okf/BUILD.md`). Every finding below is a captured result in `okf/runs/`,
not a projection. Four components, four bundles, four verdicts.

| # | Hand-built system | Bundle | Files | Verdict |
|---|---|---|---:|---|
| 1 | `docs/*.md` reference corpus | `bundles/docs` | 16 | **Genuine win for OKF** — adds a gate that exists nowhere today |
| 2 | `platform/src/pf/vendor/registry.yaml` | `bundles/vendor` | 24 | **Passes, but proves nothing** — validates structure it never checks |
| 3 | `kg/graph.json` (jaffle-shop, Table layer) | `bundles/graph-sample` | 58 | **Fails at scale** — wrong shape for a machine-derived graph |
| 4 | `kg/context_card.md` (6 projects) | `bundles/context-cards` | 6 | **No equivalent exists** — OKF has no token-budget concept at all |

---

## 1. `docs/*.md` — the one place OKF is a real gate

**Conversion:** `okf/convert_docs.py` reads all 16 files (256KB, 5,245
lines), copies bodies verbatim, prepends frontmatter (`type`, `title`,
`description`, `tags`, `status: stable`, a `generated:` stamp), and rewrites
in-corpus cross-links (`docs/POLICY.md`, bare sibling `POLICY.md`) to OKF's
bundle-relative form. Nothing else about the prose changed.

**`okf validate`** (`runs/docs-validate.json`): **10 errors**, all
`okf/links/broken`, and all real:

```
reference/air            -> ../platform/src/pf/air/sources.py
reference/air            -> ../vendor/ai-governance-framework
reference/air            -> ../platform/src/pf/ontology/policy.yaml
reference/architecture-maps -> ../platform/src/pf/architecture.py
reference/architecture-maps -> ../platform/src/pf/viz.py
reference/artifacts      -> ../platform/src/pf/artifacts.py
reference/artifacts      -> ../platform/src/pf/tools/recce.py
reference/kg-atlas       -> ../platform/src/pf/kg/
reference/project-atlas  -> ../platform/src/pf/atlas.py
reference/scaffolding    -> ../platform/src/pf/scaffold/
```

**Where this lags:** every one of these is a link from a doc to actual
*source code* in the same repo — a completely ordinary thing for
documentation to do, and something `docs/*.md` does constantly (I counted
these six files doing it before the conversion even ran). OKF's link
validator has exactly one model for a relative link: it points at another
concept in the bundle, and if the concept isn't there, it's broken. There is
no way to tell OKF "this points outside the bundle, on purpose." Every doc
that links to the code it describes will show these errors forever, which
means the *first* thing `okf validate` would need in this repo is a policy
for `../platform/`-style links (an ignore pattern, a separate "external"
link class) that doesn't exist in the tool today.

**Where it earns its score:** `okf graph` (`runs/docs-graph.json`) found
**7 of 16 docs are isolated** — zero cross-links to or from any other doc:
`ARCHITECTURE.md`, `ARTIFACTS.md`, `ENGINEERING.md`, `PROJECT-ATLAS.md`,
`STACK.md`, `VENDOR.md`, `VENDOR-CARD.md`. Nothing in this repository checks
that today — `pf arch check` verifies counts, never whether the reference
corpus actually connects to itself. `okf lint` (0 warnings) confirms my
conversion filled every recommended field, which isn't itself informative,
but running it for real rather than assuming it would pass is the point of
this exercise.

**Honest caveat:** two of the 16 files converted (`VENDOR.md`,
`VENDOR-CARD.md`) are themselves generated by `pf vendor docs` from
`registry.yaml`. Feeding a generator's output into a second generator's
input is circular — OKF validating them tells you nothing `pf vendor docs`
regenerating them wouldn't already guarantee.

**Score: 7/10.** Real, additive gate for the 14 genuinely hand-written docs.
Would need an "external link" exception before it could run in CI without
permanent false positives.

## 2. `platform/src/pf/vendor/registry.yaml` — validates, verifies nothing

**Conversion:** `okf/convert_vendor.py` reads all 24 upstream entries
(including `floci`, the one with no submodule), maps `adopted:` items onto
OKF's actual `sources[]` provenance field, and copies every `why:` /
`declined:` paragraph into the body verbatim.

**`okf validate`** (`runs/vendor-validate.json`): **0 errors.**
**`okf lint`**: **0 warnings.** `okf graph`: **24 nodes, 0 edges, 24
isolated** (vendor entries don't reference each other — expected, not a
finding).

**Where this lags — the one that matters:**

```bash
$ grep -rn "http.Get\|net/http" internal/ | grep -v _test.go
(no output)
```

`okf` makes **no network calls anywhere in its non-test code.** `sources[]`
is a string field OKF stores and echoes back (`okf show upstreams/floci`
prints `"resource": "https://github.com/floci-io/floci"`), never checked
against anything live. Run it against `floci` — the exact upstream this
session found registered in full but never wired into `.gitmodules` — and
`okf validate` reports it exactly as healthy as the 23 that are actually
pinned. This is not a bug in my conversion; it's what OKF's spec is for:
static structural validation of a markdown bundle, not liveness.

Compare to what this repository already runs: `pf vendor verify` checks
three *executable* schema contracts (declared paths still resolve, `otop`/
`mdl`/loop-registry structural conformance), and `.github/workflows/vendor-pins.yml`
does a real `git ls-remote` + `git fetch --depth 1 <sha>` against all 23
pins daily — the thing that would have caught `jagmarques/asqav-compliance`
being deleted the same day, not three days later. OKF has no equivalent to
either, and its schema has no field that could hold one — `sources[]` has
no health-check hook, no "last verified reachable" timestamp, nothing.

**Score: 2/10.** It parses the registry's shape and finds nothing wrong,
which is true but nearly worthless — the registry's entire value is in
catching what changed or disappeared upstream, and OKF's validator is
structurally incapable of that class of check.

## 3. `kg/graph.json` (jaffle-shop) — wrong shape at scale

**Conversion:** `okf/convert_graph_sample.py` takes the **raw Table layer
only** — 57 `Table` nodes and their one `Source`, out of jaffle-shop's full
4,574-node graph. Columns are embedded as a markdown schema table inside each
Table's body (matching OKF's own reference convention in
`testdata/valid/tables/events_.md`), not split into one file per column —
the fairest reading of "one concept, one file."

```
57 Table concepts, 1 Source concept
total bundle size: 28,430 bytes  (58 files)
committed kg/graph.json:  2,636,335 bytes  (1 file, 4,574 nodes, 15 kinds)
```

That's **6.6% of the graph's nodes by count** — the smallest of its eight
"file-worthy" kinds — already at 58 files. `okf validate`
(`runs/graph-sample-validate.json`): 0 errors, 30ms. `okf graph`
(`runs/graph-sample-graph.json`): 58 nodes, 57 edges, 0 isolated —
correctly reconstructs the one-source-fans-out-to-57-tables shape via
`backlinks sources/jaffle-seeds` (57).

**Where this lags — two separate problems, not one:**

**(a) File-count explosion.** The full graph has 15 node kinds. Excluding
the three that are naturally embedded rather than standalone (`Column`
2,392, `Property` 298, `Test` 540 — the same treatment I gave Table's
columns), the remaining "concept-worthy" kinds total:

```
Table 57 · Model 1,088 · Concept 68 · Policy 32 · Dimension 25 · Exposure 22
· Metric 19 · Evidence 15 · Relation 14 · Decision 2 · Project 1 · Source 1
= 1,344 files, from ONE project, regenerated on every dbt build
```

`gate.yaml`'s `maxFiles: 12` — the cap this repo already enforces per commit
— would reject the very first `pf kg build` re-run under this model outright.
The current design (one `graph.json`, one diff) is not an arbitrary choice;
it's the only shape compatible with a graph that changes on every build
across 11 projects.

**(b) Edge typing.** The real graph has **13 distinct edge kinds** —
`has_property`, `feeds`, `measures`, `tested_by`, `has_column`, `domain_of`,
`range_of`, `grouped_by`, `governs`, `contains`, `decides`, `evidenced_by`,
`instantiates` — and `pf impact` / `kg_neighbors` / `kg_path` all reason
*by kind* (impact analysis walks `feeds`/`measures` edges specifically, not
"any link"). `okf graph`'s edge objects are `{"from": ..., "to": ...}` —
no `kind` field exists anywhere in the schema. Converting the full graph
to OKF wouldn't just multiply the file count; it would collapse 13
semantically distinct relationships into one undifferentiated line, and
`pf impact-gate` — the actual merge gate — has no way to run on what's left.

**Score: 1/10.** Structurally validates at the sample I built; both of the
reasons it can't scale to the real thing are architectural, not
incidental — more conversion effort doesn't fix either one.

## 4. Context cards — the dimension OKF doesn't have

**Conversion:** `okf/convert_docs.py`'s sibling script converted 6 real
`kg/context_card.md` files (chosen to span the size range) into OKF
concepts, frontmatter only, bodies untouched.

```
acme/acme-eu               1,835 bytes  (~458 tokens)
acme/acme-us               1,951 bytes  (~487 tokens)
commodity/commodity-india  5,155 bytes  (~1,288 tokens)
globex/globex-core           409 bytes  (~102 tokens)
jaffle/jaffle-shop          6,342 bytes  (~1,585 tokens)  <- over its 1,500 budget
zenith/zenith-de              407 bytes  (~101 tokens)
```

`okf validate`: 0 errors on all six, jaffle-shop included.

**Where this lags:** there is no lag to measure, because there is no field
to fail. `pf.kg.card.PROJECT_CARD_BUDGET = 1500`, `ROUTER_BUDGET = 700`,
`PROJECT_CLAUDE_BUDGET = 600`, `GROUP_CLAUDE_BUDGET = 400` — every one of
this platform's always-in-context artefacts has a hard ceiling `pf tokens`
enforces in CI, because (per `pf.kg.card`'s own docstring) "the always-on
tier is what silently inflates every session." jaffle-shop's card sitting at
1,585/1,500 is a real, currently-uncaught failure on `main` (see the
`jaffle-shop-context-card-over-budget` memory from this session) — and OKF's
spec has no concept that could express it. Not `status`, not `stale_after`,
not a custom `Extensions` field with meaning to the CLI: `okf validate`/
`lint` have no notion of "count this file's tokens and fail past N."

**Score: n/a — wrong tool, not a graded one.** OKF was never built for a
budget-enforced artefact; there's nothing here to replace.

---

## Overall

Nothing in the graph/provenance/card stack is a candidate for replacement —
each was shaped by a constraint (regeneration scale, a hard token ceiling,
tamper-evident chains, live reachability checks) that OKF's spec doesn't
share and has no field to grow into. The one real, actionable outcome of
this run: **add `okf validate`/`lint` over `docs/*.md` as its own new CI
gate**, once it has a way to exempt links into source code — additive,
narrow, and it catches something (7 orphaned docs) that exists in this
repository right now and that nothing currently checks.

## Reproducing this

```bash
go build -o /tmp/okf-bin/okf github.com/Atomz-org/okf/cmd/okf   # or: cd <clone> && go build ./cmd/okf
uv run python okf/convert_docs.py
uv run python okf/convert_vendor.py
uv run python okf/convert_graph_sample.py
/tmp/okf-bin/okf validate okf/bundles/docs
/tmp/okf-bin/okf graph okf/bundles/docs
# etc. — every command run for this report is in okf/runs/*.json
```

The `okf` binary itself is not committed here (Go binaries aren't checked
into this repo, and adding `okf` as a new `vendor/` submodule is the human
decision this repo already reserves — see the `floci-vendor-pin-missing`
memory for exactly that call being left unmade on purpose).
