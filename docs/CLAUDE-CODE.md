# Claude Code, as configured here

The power-user setup for this monorepo: what is wired, where it lives, and which
widely-circulated advice does not apply. Not loaded into any session — read it
when changing the session layer, not while working.

Adapted from [claude-code-for-power-users][guide]. That guide is a good map of
the *shape* of a serious setup; a fair amount of its concrete detail no longer
matches the product. The last section says exactly which parts.

[guide]: https://github.com/PackMaaan/claude-code-for-power-users

---

## Where everything lives

| Layer | Path | Scope |
|---|---|---|
| Router memory | `CLAUDE.md` | repo-wide, always loaded |
| Project memory | `groups/<g>/projects/<p>/CLAUDE.md` + `kg/context_card.md` | one entity, always loaded, **budgeted** |
| Marketplace | `platform/.claude-plugin/marketplace.json` | lists all 19 plugins |
| Toolkits | `platform/toolkits/<name>/` | one craft each, enabled per project |
| Session layer | `platform/toolkits/power-tools/` | commands, agents, hooks, MCP |
| Root settings | `.claude/settings.json` | platform sessions |
| Project settings | `groups/<g>/projects/<p>/.claude/settings.json` | generated by `pf new-project` |
| Policy | `gate.yaml` + `gate.capabilities.yaml` | enforced by two hooks and CI |

Two commands cover normal use:

```bash
uv run pf work <group> <project>   # a session scoped to one entity
uv run pf --help                   # everything else
```

`pf work` chdirs into the project and execs `claude`, which is what makes the
project's settings, plugins, MCP server and card the ones that load. Running
`claude` from the repo root instead gives you a *platform* session — different
scope, different permissions, no warehouse tools.

## 1. Memory: CLAUDE.md

The guide's advice is "put everything in CLAUDE.md". Here that is wrong, and the
repo enforces the opposite: `pf tokens` fails the build when a card or project
`CLAUDE.md` exceeds its budget, because always-on context is paid by every
request for the life of the project.

The structure instead:

- **Always on, budgeted** — the router (`CLAUDE.md`), the project card
  (`kg/context_card.md`, generated by `pf kg card`), the group card. Facts that
  every turn needs.
- **On demand** — skills in the toolkits. Loaded when their description matches
  what you are doing, free otherwise.
- **Queried** — the knowledge graph. Never loaded; asked.

So a new fact goes in the layer that matches how often it is needed. Business
rules the graph cannot encode go in the project `CLAUDE.md` under that heading.
Anything derivable from the models belongs in the graph, not in prose.

```bash
uv run pf tokens          # the budget, enforced
uv run pf kg card <g> <p> # regenerate a card rather than hand-trimming it
```

## 2. Context management

The guide's answer to a large codebase is scope flags. Those flags do not exist.
The real levers here, cheapest first:

| Instead of | Do |
|---|---|
| reading models to find a dependency | `kg_neighbors`, `kg_path` |
| grepping for where a concept is used | `kg_search` |
| reading downstream models to judge a change | `impact_analysis` |
| loading a whole project | `/gemini-analyze`, scoped to one project dir |
| carrying an old task's context | `/clear` |

`/context-budget` reports where the session's always-on context is going.

**One entity per session.** Never read another group or sister project. Business
logic does not transfer between entities, so an assumption carried across is a
bug — and the settings deny the read, in both directions.

## 3. Tools: the MCP server

`platform/toolkits/power-tools/.mcp.json` starts `pf mcp` as the `pf` server.
23 tools, scoped to one project by `PF_PROJECT_DIR` (falling back to cwd):

- **graph** — `kg_search`, `kg_neighbors`, `kg_path`, `impact_analysis`
- **warehouse** — `list_tables`, `preview_table`, `execute_sql_query`,
  `display_schema`, `get_row_counts`
- **dbt** — `dbt_list`, `dbt_build`, `dbt_test`, `get_model_details`
- **metrics** — `list_metrics`, `get_dimensions`, `query_metrics`
- **ontology** — `ontology_classes`, `validate_annotations`
- **pipelines / secrets** — `get_local_pipeline_state`, `secrets_view_redacted`,
  `secrets_update_fragment`
- **toolkits** — `list_toolkits`, `toolkit_info`

Every data-returning tool truncates: schema, ≤20 rows, summary stats. Never a raw
dump. That policy is the cheapest defence against a context blowup, and it lives
in the server rather than in an instruction anyone can forget.

In a **root session** there is no active project, so warehouse and graph tools
answer "not inside a project". That is the isolation working.

```bash
uv run pf mcp        # run it by hand
just mcp
```

## 4. Commands

In `platform/toolkits/power-tools/commands/`. The guide's six, plus three this
platform can actually answer.

| Command | Does |
|---|---|
| `/security-audit` | secrets at rest, gate holes, PII in committed recce artefacts |
| `/performance-audit` | dbt timing from `run_results.json`, DuckDB plans, dlt throughput |
| `/architecture-review` | ontology conformance, declared joins, grain, layering |
| `/tech-debt` | inert governance first, then model/source/doc debt |
| `/blast-radius` | what breaks if a node changes — run **before** editing |
| `/ship` | gate → check → build → recce → one conventional commit |
| `/context-budget` | where always-on context goes, and how to get it back |
| `/gemini-analyze` | hand a repo-sized question to a bigger window |
| `/ast-grep` | structural search (requires `brew install ast-grep`) |

Each keeps the guide's generic checklist at the bottom, for the cases the
platform-specific procedure does not cover.

## 5. Subagents

In `platform/toolkits/power-tools/agents/`. All four are **read-only** — they
declare `disallowedTools: Write, Edit, MultiEdit, NotebookEdit`. A verifier that
can edit stops being a second opinion and becomes a second author.

| Agent | Catches |
|---|---|
| `impact-verifier` | downstream that *silently changes value*, which a dependency list does not distinguish from "recompiles" |
| `sql-reviewer` | grain violations, fanout, null-swallowing joins, wrong `unique_key` |
| `secrets-auditor` | credentials and PII in tracked files, history, and committed artefacts |
| `semantic-conformance` | broken links in ontology → annotation → model → metric → contract |

Invoke by asking for one by name, or let the model pick from the description.

## 6. Hooks

Four events, configured in `platform/toolkits/power-tools/hooks/hooks.json` plus
the pre-existing gate.

| Event | Script | Effect |
|---|---|---|
| `PreToolUse` | `platform/hooks/pre_tool_use.py` | **blocks** writes to generated artefacts, secrets and shared infra; prints blast radius for models and sources |
| `PostToolUse` | `scripts/format_edit.py` | `ruff format` + import sort on `.py`; `sqlfluff fix` on dbt `.sql` |
| `SessionStart` | `scripts/session_start.sh` | injects branch, active entity, and whether the graph is present/stale |
| `Stop`, `Notification` | `scripts/notify.sh` | desktop notification + spoken line + append-only log |

Two design rules worth keeping if you edit them:

- **The formatter never removes code.** Autofix is restricted to import sorting
  (`--select I`). A bare `ruff check --fix-only` deletes unused imports, and an
  import added moments before the code that uses it is legitimately unused. A
  hook that removes what the agent is about to use is worse than no hook.
- **SQL that will not parse is skipped, not half-formatted.** Models using
  project macros template to an unparsable tree under the stubbed `jinja`
  templater; sqlfluff refuses to rewrite those, and the hook stays quiet.

Notifications, off switches:

```bash
PF_NOTIFY=0        # silent
PF_NOTIFY_VOICE=0  # desktop only
PF_NOTIFY_LOG=...  # default ~/.claude/pf-task-log.txt
```

Set in `.claude/settings.json` under `env`.

## 7. Permissions

`permissions` in `.claude/settings.json`, at root and per project. Not
`.claude/permissions.json` — that file does not exist in any current version.

- **deny** — reading `.env*`, `**/secrets.toml`, `**/credentials/**`; writing
  `vendor/**`; and per project, reading any sister or other group.
- **ask** — `git push`, `gh pr create`, `gh pr merge`, submodule updates.
- **allow** — the `pf`, `dbt`, `mf` and read-only `gh` verbs used constantly.

Permissions and the gate are different mechanisms and both are needed:
permissions decide whether a *tool call* happens, `gate.yaml` decides whether a
*path* may change, and the gate also runs in pre-commit and CI where no agent is
involved.

## 8. Enforcement outside the session

```bash
just hooks                 # install .git/hooks/pre-commit (not cloned with the repo)
uv run pf gate --paths a,b # the same policy, by hand
uv run pf check            # conformance + blast radius of your changes
uv run pf loop audit       # scored readiness: gate, hooks, marketplace, MCP, graphs
```

`pf loop audit` is the one to run after changing anything in this document's
scope. It scores the session layer, including two checks that exist because this
exact configuration silently broke once: **plugin marketplace resolves** and
**MCP tools available to projects**.

CI is **one workflow per project**, named after it: `.github/workflows/<project>.yml`
holds every job that project runs (`impact-gate`, `recce`, and whatever a future
capability adds). It is generated by `pf bootstrap` from the `ci_jobs` each
capability declares — do not hand-edit it; change the capability. A `changes` job
diffs the PR once and publishes a boolean per area, and every job guards on it,
so editing a page never starts a dbt review.

Repo-wide workflows sit alongside: `pr-report.yml` (impact report on every PR),
`vendor-sync.yml`, and `claude-review.yml` — the last is opt-in, triggered by
adding the `claude-review` label, because it is billed per run.

## 9. Extended thinking

`think` → `think hard` → `ultrathink`, in the prompt. Worth reaching for on
ontology changes, anything touching a published contract, and any change whose
blast radius crosses into metrics. Not worth it for a staging model.

`MAX_THINKING_TOKENS` is deliberately **not** set here. It is a *cap*, not a
boost — setting it to the number the guide suggests can lower the budget rather
than raise it, depending on model and effort level. Leave it unset unless you are
deliberately constraining spend.

## What in the source guide does not work

Following these verbatim wastes time. Current as of Claude Code 2.1.x.

| Guide says | Reality |
|---|---|
| `.claude/permissions.json` | No such file. `permissions` lives in `.claude/settings.json`. |
| `claude --scope=` / `--exclude=` / `--include=` | No such flags. Scope by cwd (`pf work`), and by asking the graph instead of reading files. |
| `claude --max-context=` / `--clear-context` | No such flags. `/clear`, and `autoCompactWindow` in settings. |
| `/clear --conversation-only`, `--rescan-project`, `--except=` | `/clear` takes no arguments. |
| `claude --session=` / `--resume=<name>` | `--resume` takes a session id, not a name; `-c` continues the last one. |
| `claude --confirmation-required` | Not a flag. Use `permissions.ask`. |
| `claude auth login` | Not a subcommand. `/login` in-session. |
| `config.json` with `temperature`, `thinking_budget`, `allowedTools` | Not the schema. Settings keys are documented under `.claude/settings.json`. |
| `DISABLE_TELEMETRY`, `DISABLE_ERROR_REPORTING` | Not current names. Telemetry is opt-**in** via `CLAUDE_CODE_ENABLE_TELEMETRY`. |
| `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, `DISABLE_NON_ESSENTIAL_MODEL_CALLS`, `ENABLE_BACKGROUND_TASKS`, `FORCE_AUTO_BACKGROUND_TASKS` | Not in the documented environment set. |
| `CLAUDE_CODE_CONTAINER_MODE`, `BYPASS_ALL_CONFIRMATIONS` | Invented. `--dangerously-skip-permissions` is the real thing, and is for disposable containers only. |
| `claude mcp restart --all` | Not a subcommand. `/mcp` in-session. |
| `/commands` to list custom commands | `/help`, or `claude plugin details <plugin>`. |
| Marketplace `source` paths relative to `marketplace.json` | They resolve from the **marketplace root** — the directory holding `.claude-plugin/`. Getting this wrong silently loads zero plugins, which is what happened here. |

What the guide gets right, and is worth keeping: CLAUDE.md as the highest-leverage
file, custom commands as the way to encode a team's process, hooks as the way to
make a rule fire without an agent remembering it, subagents for verification, and
"plan before implementing" as the default posture.
