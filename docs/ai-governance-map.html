AI Governance Map

What happens between an agent proposing a metric and that metric existing: the seven steps every proposal takes, what each one refuses, what the ledger keeps, and what a person still decides. Every entity, every harness, one engine.

Four ways a proposal ends

Every path reaches the provenance chain, and each ends in the pairing the chain audit checks: a denied or held decision must be followed by a blocked execution, an allowed one by a successful execution. A rejection that executed anyway, or one that was never written, would fail pf provenance verify.

PASS
decision allow · execution ok

Every check holds. The record is written under governance/metrics/<mart>/<metric>.json and the chain position is returned.

REJECT
decision deny · execution blocked

A check failed. The findings are in the record; the payload is not, only its SHA-256.

ESCALATED
decision hold · execution blocked

The target is elevated. A person approves the action id, the agent resubmits with it.

CIRCUIT_BROKEN
decision deny · execution blocked

Too many rejections in a row for this entity. A person resets the breaker with a reason, and the reset is itself a chain record.

3
Action gate
enforced

May this role write this path?

Blueprint: path permission verification against gate.yaml; immutable roots for provenance/, gate.yaml, loop-constraints.md and .github/; human elevation for protected analytics.

Three questions in a fixed order. First the repository's own path policy, gate.yaml, consulted as a project session: credential files, generated artefacts, the provenance record, shared platform code are denied to an agent whatever else is configured, and nothing in the engine can widen that. Second, the entity's roles: governance/aidf.yaml says which agent may write under which globs. The floor lets metric-gap-harvester write under governance/metrics/** and platform_orchestrator under that and governance/semantic/**; a role that is not declared may write nothing. Third, elevation: a target matching one of the entity's elevated paths, by a role not in its elevated roles, is held for a person rather than refused or allowed.

Refused by name, always

  • provenance/, .github/, vendor/, platform/
  • gate.yaml, gate.capabilities.yaml, loop-constraints.md, LOOP.md
  • pyproject.toml, uv.lock, AGENTS.md, CLAUDE.md
  • any target with .. or an absolute path: not a project path at all

Declared per entity

runtime:
  roles:
    metric-gap-harvester:
      targets: ["governance/metrics/**"]
  elevated:
    paths: ["governance/metrics/regulatory_*/**"]
    roles: ["lead_risk_officer"]

Example

The harvester proposes capital_ratio on regulatory_capital for acme-eu, whose overlay lists governance/metrics/regulatory_*/** as elevated. The gate answers hold / human_oversight; the chain records intent, the hold and a blocked execution; the outcome is ESCALATED with the action id. A risk officer runs pf provenance approve <id> --note "reviewed", the harvester resubmits with --approved <id>, and the same payload now passes with the decision reading allow / human_oversight. Nothing was written in between.

4
Contract
enforced

Does the payload have the shape a metric has?

Blueprint: schema enforcement with Pydantic v2 strict models — MartMetricContract, SemanticModelContract.

Strict, frozen and closed, and validated in strict JSON mode because that is the mode an agent's output is in: a number must be a JSON number, a string a JSON string, an unknown field is a rejection rather than a silent drop, an enum arrives as its value and a timestamp as RFC 3339 text. The mart name is not a platform constant. The floor accepts any snake_case identifier and each entity tightens it in its overlay (mart_pattern: "^fct_[a-z0-9_]+$"), so one class serves a thousand marts under a dozen naming conventions.

FieldRuleWhy
mart_name2–128 chars, the entity's patterna mart outside the convention is a typo or a guess
metric_namesnake_case, 2–64 charsit becomes a MetricFlow identifier
aggregation_typeSUM · COUNT · COUNT_DISTINCT · AVG · MIN · MAX · MEDIAN · PERCENTILE · RATIO · DERIVED, exact casethe operator fixes the calculation's meaning
sql_definition5–4096 chars; judged by the AST validator nextbounded so a prompt injection cannot arrive as a definition
dependent_columns1–64 identifiers, no repeats; must cover what the SQL readsthe agent's own claim of what it touched, checked against the truth
author_agentthe loop, harness or personwho to ask
status, created_at_utcdefaults provisional and now, UTC onlya metric is provisional until a person verifies it

Example

{"mart_name": "orders", "metric_name": "order_count", "aggregation_type": "COUNT",
 "sql_definition": "SELECT COUNT(order_id) FROM orders",
 "dependent_columns": ["order_id"], "author_agent": "metric-gap-harvester"}

Passes. The same payload with "aggregation_type": "count" is rejected at this step with schema / enum at aggregation_type; with "override_gate": true added, with schema / extra_forbidden. Nothing further runs on a payload that has no shape.

5
Validators
enforced

Is the SQL a read-only projection of real columns, and is there anything in it that should not leave?

Blueprint: semantic AST SQL validation to detect hallucinated columns and tables, and automated PII masking and confidential token redaction.

The SQL is parsed with sqlglot in the entity's dialect (DuckDB by default; Snowflake, BigQuery, Postgres when the overlay says so), not matched with a regular expression. The catalogue it is checked against is the entity's own knowledge graph, the same kg/graph.json the impact gate reads, so the engine never has to be told a schema and never trusts the agent's account of one. When no catalogue is available the decision record says catalog: absent; it does not pass silently.

The AST validator refuses

  • DDL, DML, transaction control, COPY, ATTACH, SET, PRAGMA, anything the parser could not classify
  • a second statement after a semicolon
  • SELECT * and t.* (COUNT(*) is fine)
  • information_schema, pg_catalog, sys, duckdb_internal
  • read_parquet, read_csv, getenv, glob, external scans
  • a column or table the catalogue does not have
  • a column the SQL reads that dependent_columns does not declare

The PII scrubber refuses

  • private keys, AWS access keys, GitHub tokens, JWTs, bearer tokens
  • password =, api_key: and similar with a value
  • e-mail addresses, IPv4 addresses, IBANs
  • in every string field of the payload, with the field's path

It reports the kind and the offset, never the value, so a rejection record cannot become the leak it prevented. An entity may allow-list a documented service address with a regex; each entry is a decision.

Example

On jaffle-shop the graph says orders has order_id, customer_id, order_date, amount, status. A proposal with SELECT SUM(customer_ltv) FROM orders is rejected: sql_ast / hallucinated_column: ['customer_ltv']. A proposal whose rationale reads "ask jo@example.com if unsure" is rejected with pii / email at offset 4 (14 chars), and the address is in neither the chain nor the finding. A proposal reading SELECT SUM(amount) FROM orders WHERE status = 'paid' with dependent_columns: ["amount"] is rejected with undeclared_column: ['status']: it read more than it admitted.

6
Ledger
enforced

What is kept, and what is deliberately not

Blueprint: append a verification payload to the provenance/ chain with a SHA-256 link; a strictly monotonic sequence, a previous hash, a status in {PASS, REJECT, CIRCUIT_BROKEN, ESCALATED}.

The engine writes into the chain the platform already had, provenance/chain.jsonl, five stages, RFC 3161 and OpenTimestamps anchors, rather than a second ledger beside it. Three records per proposal share one action id. The intent carries the role, the contract and the payload's SHA-256. The decision carries the verdict, the rule that produced it, and the findings. The execution carries the status and, on a pass, the written record's own SHA-256. The payload itself is never written to the chain: an auditor can prove which bytes were judged without the ledger holding an e-mail address the scrubber caught.

The breaker keeps no file of its own. It counts consecutive REJECT executions for the entity backwards through the chain until it meets a PASS or a reset marker, so a restart cannot forget the count and deleting a file cannot clear it. pf govern breaker <group> <project> --reset --reason "fixture mart" writes the marker, with the reason and the actor.

One engine, every entity, every harness

The engine is built from (group, project) and nothing else. Its rules come from three layers, each tightening the one before, and a project with no overlay at all is governed by the floor: a project scaffolded before this existed is not ungoverned, and every project pf new-project creates gets the seeded, inert overlay from the default-enabled aidf capability.

LayerFileMay only
Platform floorplatform/src/pf/aidf/data/defaults.yamlbe the baseline for every entity
Familygroups/<group>/aidf.yaml (optional)lower a budget, shorten a patch window, add a validator, narrow the mart pattern, add elevated paths, decline an article with a reason and an owner. Loosening raises AidfRelaxation at load time.
Entitygroups/<group>/projects/<project>/governance/aidf.yaml (seeded)

From a shell

pf govern check [group [project]]
pf govern schema mart_metric
pf govern prompt <g> <p> <mart> <metric>
pf govern evaluate <g> <p> --payload p.json \
   --role metric-gap-harvester [--no-write]
pf govern breaker <g> <p> [--reset --reason ".."]

exit 0 PASS · 1 REJECT · 2 ESCALATED · 3 CIRCUIT_BROKEN

From any harness that speaks MCP

The pf server exposes govern_metric(payload_json, role, target, contract) and govern_prompt(mart_name, metric_name). Claude Code, Cursor, Copilot, Codex, Gemini CLI and a local Qwen through OpenCode all reach the same engine; there is no per-vendor code path, which is what makes the framework model-agnostic. The prompt embeds the contract's JSON schema, so what a model is told and what judges it cannot drift apart.

What each scope does with it

  • Session (Claude Code, Codex CLI, Cursor agent, Gemini CLI): produce contract JSON and submit it through pf govern evaluate or govern_metric; never write under governance/metrics/ by hand.
  • Autonomous (@claude in Actions, Jules, the Copilot coding agent): a REJECT is final for the run, so fix the payload and never the rule; ESCALATED waits for a person; CIRCUIT_BROKEN ends the run and the pull request says so.
  • Inline (completions): reference only columns the file or the architecture map already names; never DDL or DML; never provenance/, gate.yaml, LOOP.md, .github/.
  • Local model (Qwen on mlx or Ollama): emit a verification block naming the tables and columns you intend to use and confirm each against the approved list before the JSON.
  • CI glue (any model writing workflows): uv run, uv sync, uvx only; commands like prowler, trivy and guardrails are installed isolated, never added to the workspace lockfile.

Settings

None. Pillar one needs no secret and no variable: it runs from the checkout, reads the entity's overlay and knowledge graph, and writes to the chain the hooks already write to. The only choices are in each entity's governance/aidf.yaml, and each one may only tighten the floor:

runtime:
  sql_dialect: snowflake                      # when the production warehouse is not DuckDB
  mart_pattern: "^(fct|dim|agg)_[a-z0-9_]+$"  # the entity's convention
  validators: [schema, sql_ast, pii]          # may grow, never shrink
  roles: { metric-gap-harvester: { targets: ["governance/metrics/**"] } }
  elevated: { paths: ["governance/metrics/regulatory_*/**"], roles: ["lead_risk_officer"] }
  pii: { allow: ["svc-metrics@example\\.com"] }
  budgets: { max_iterations_per_invocation: 50, max_consecutive_validation_failures: 3 }

Two knobs deserve a person's attention rather than a default: the elevated paths, which are where "this mart needs a human" is declared, and the mart pattern, which is the cheapest hallucination check there is.

What stays a person's

  • Verifying a metric. Everything the engine accepts is provisional; verified is a status a person sets after reading the SQL and the numbers.
  • Approving an elevated write, and resetting a breaker, each with a reason that the chain keeps.
  • Deciding an entity's roles, its elevated paths and its mart pattern.
  • Reading the chain. pf provenance verify proves it holds together; only a reader notices that what it holds is wrong.
