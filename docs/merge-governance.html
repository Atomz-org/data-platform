01 · The funnel

Merging is a narrowing, not a trigger

Every workflow below fires on pull_request. Only two of them also declare push: branches: [main], so only two survive the merge. That is a deliberate design — the per-project checks exist to judge a diff against its base, and a merge commit has no base to judge against. The consequence is still worth seeing plainly.

03 · Concurrency

A fast queue cancels its own audit trail

The workflow declares concurrency: ai-governance-${{ github.ref }} with cancel-in-progress: true. On a pull request the ref is unique per branch, so this is exactly right. On main the ref is always refs/heads/main — so every merge cancels the still-running governance check of the merge before it.

04 · Before the merge

Where the governance that works actually happens

This is the reassuring half. On a pull request, each project workflow first runs a changes job that turns the diff into five booleans, and every downstream job is conditioned on one of them — so governance scales with what was touched rather than running everywhere every time.

05 · Findings

Five things to change

M1The post-merge governance check has never passedcritical

47 runs, 30 failed, 17 cancelled, 0 succeeded. Two of three jobs die at a recursive checkout because the vendor/asqav-compliance upstream is gone. A permanently red required-looking check is worse than no check: it trains everyone to ignore the one signal that is supposed to mean something.

fixRe-point or drop the dead submodule. Bumping a pin is a human decision, so this one needs an owner, not an agent.

M2Merges cancel each other's governance runhigh

The concurrency group keys on github.ref, which is constant on main. Correct for pull requests, wrong for pushes: during a batch landing, each merge kills the audit of the one before it. The faster the team ships, the less of this runs.

fixKey the group on github.sha for pushes, or set cancel-in-progress: ${{ github.event_name == 'pull_request' }}.

M3The ledger audit runs where the evidence isn'tmedium

The docs call pf provenance verify the blocking check in CI. In practice the ledger is gitignored runtime state, so a checkout never has one and the step always skips. The reasoning is sound — a source checkout holds no runtime evidence — but the effect is that the audit never runs anywhere CI can see.

fixVerify an exported bundle, or run the audit on a schedule against a long-lived environment that actually has a chain.

M4One project is missing three governance jobsmedium

commodity-india has no air-baseline, no kg-current and no architecture job. The workflows are generated by pf bootstrap from each project's capabilities, so this is a capability gap showing through — but nothing in CI compares one project's job list to its siblings', so it stays invisible.

fixRegenerate the workflow, and add a check that every project's generated jobs match its declared capabilities.

M5A green tick that means "nothing to check"low

The Provenance chain job reports success having verified no ledger. It is honest in its log and misleading on the checks list. The 23 tamper tests it does run are real and valuable — they are just a test of the detector, not of the evidence.

fixReport the skip as a distinct neutral conclusion, so "passed" and "had nothing to look at" are not the same tick.
