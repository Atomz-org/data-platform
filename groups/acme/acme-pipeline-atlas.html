What each layer owns

dlt

Projects declare, the platform wires

A project writes @dlt.resource plus @annotate. It never names a destination — build_pipeline() does, as {project}_{source} against the project's DuckDB file.

DuckDB

One file, one entity

acme_us.duckdb and acme_eu.duckdb never meet except through the roll-up, which attaches both READ_ONLY and detaches after. Each project gets its own writer pool so sisters never queue behind each other.

dbt

Staging mirrors the source

One staging model per dlt resource, then marts. The dbt source is what ties back to the dlt asset that landed it.

Dagster

One code location per project

definitions.py is ten lines; build_definitions() assembles everything. dbt models are emitted through @dbt_assets rather than one shelled-out dbt build — because a single opaque asset draws no edges.

Four decisions worth knowing

  • The annotation is the contract, not a hint. Roles attached at ingest drive staging generation, PII policy, statistical monitors, graph edges and conformance. money_amount becomes a sum-drift monitor; event_time becomes a freshness check.
  • Columns evolve, data types freeze. The default schema contract is tables: evolve, columns: evolve, data_type: freeze. Resilient to a new field; unwilling to let a renamed endpoint quietly create a parallel table nobody models.
  • Lineage is why dbt is not shelled out. The translator maps each dbt source onto the dlt asset that lands it. That mapping is the only thing stitching ingestion and transformation into one graph.
  • The roll-up never imports a sister. It depends on plain AssetKeys pointing into the sisters' code locations, and reads their data through a read-only ATTACH. Business logic does not cross the boundary — only numbers do.
