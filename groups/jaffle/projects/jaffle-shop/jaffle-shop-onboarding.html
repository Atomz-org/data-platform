Onboarding Jaffle Shop Expanded

A 1,058-model dbt project from DataRecce/jaffle-shop-expand, brought into the platform. The SQL is the easy half. The semantics, and the platform's own scale limits, are the real work.

DataRecce/jaffle-shop-expand → groups/jaffle/projects/jaffle-shop · DuckDB first, Snowflake once dev is green

Verdict

Mechanically this lands in about a day, and the tooling to do it is built. The blocker is not code — it is that the platform's ontology has no concepts for half of what this project models. That is a platform-tier decision, and it has to be made before a single file is copied.

Below it sits one real technical risk, and it is the quiet kind: 128 SQL call sites that run without error on the target and can still return the wrong number.

What the source actually is

Its README is explicit: "a realistic mock data warehouse for testing dbt tools, PR review workflows, and data platform capabilities." This is Recce's scale fixture, built on dbt-labs/jaffle-shop — not a company's warehouse. That matters for how much semantic investment the synthetic domains deserve.

It is also unusually clean to move: no Python whatsoever. No Airflow, no Prefect, no Dagster, no dlt. Just dbt, seeds and macros.

Where it lands

A new group, jaffle, with one project, jaffle-shop. Not inside acme, globex or zenith.

A group in this platform asserts something specific: sister companies sharing an ontology instance, conformed dimensions and group metrics, with a roll-up that unions across them. Dropping a sandwich-shop chain beside an existing family would assert conformance that does not exist, and the roll-up would be the thing that breaks. A new group costs one pf new-group and keeps the claim honest.

Per the repo's own rule I did not read the other groups' business logic to reach this — the argument is structural, not comparative.

What actually blocks

Four things, in the order they have to be resolved.

Decision

The ontology has no concepts for most of this project

Ontology v2 has 16 concepts, shaped for subscription commerce: Customer, Order, Product, Location, Employee, Payment, Subscription, Interaction…

Four of the six core jaffle tables map cleanly — customers, orders, products, stores. Two do not: raw_items (order lines) and raw_supplies (per-SKU cost inputs) have no concept at all. Beyond the core it gets worse: supply chain needs Supplier, PurchaseOrder, Shipment, Inventory; HR needs Department and Position; marketing needs Campaign. None exist.

The 16 roles are fine — they are generic enough to carry any of this. It is purely a concept gap. Extending the ontology is a platform-tier change affecting every existing group, so it is your call, not a step in this plan.

Withdrawn

The context card fits fine — this blocker was mine, and it was wrong

I reported that 1,058 models could not fit the 1,500-token card budget, at roughly 3× over in the most compressed form. That was wrong, and building the check properly disproved it.

pf kg card does not enumerate every model. Each section truncates at a fixed limit, so its output is bounded regardless of project size — measured: 3 marts render in 3 lines, 772 marts in 13 lines and 364 tokens, identical to 100 marts.

What is genuinely true is smaller and different: a card naming 12 of 772 marts is inside budget and nearly uninformative. So the card now rolls the remainder up by tag rather than only counting it — …and 760 more — by domain: marketing (128), hr_ops (128), supply_chain (127)… — which costs one line and describes all of them. jaffle's domain: tags make that work out of the box. All seven existing cards regenerate byte-identical.

Decide

maxFiles: 12 versus a 1,058-model project

The gate caps a loop run at 12 files. That is a sensible ceiling for a 9-model project and an almost meaningless one here — a single tag rename across marts/finance touches 29. Agent loops will be unable to do useful work on this project without either a per-project override or an explicit decision that loops don't run here.

I'd leave the cap alone and exclude this project from loops until it earns its way in. Raising a global safety limit to accommodate one imported fixture is the wrong trade.

Tooling

pf onboard is not on this branch

The branch is feat/-project-onboarding-from-github, but the onboarding code lives on feat/adding-context-and-rules — this branch has only a stale __pycache__ where platform/src/pf/onboard/ should be, and no context.py.

Related and worth fixing regardless: TOOLKITS.md and seven kg/tools_card.md files are committed here, but the generator that produces them is not. Nothing on this branch can regenerate or validate them, and on the other branch they are gitignored as build output.

Cherry-pick the onboard and context modules across before starting, or Phase 1 is a manual copy with no survey, no capability reconciliation and no plan/apply split.

What looks hard and isn't

Built

The SQL is portable through a macro toolkit — no per-database rewrite

There is now a dbt-snowflake toolkit on macro-paths for every project. Its sf_* macros compile to whatever the target adapter understands, so one set of models runs on DuckDB in development and Snowflake in production — and on Postgres or ClickHouse without further work.

select {{ sf_iff("status = 'paid'", 'amount', '0') }} as paid

DuckDB / Postgres → case when status = 'paid' then amount else 0 end
Snowflake         → iff(status = 'paid', amount, 0)
ClickHouse        → if(status = 'paid', amount, 0)

29 macros, each asserted against a real dbt run. Three reproduce Snowflake's semantics against DuckDB's native behaviour, which is the reason the toolkit exists rather than a find-and-replace:

  • sf_least(['a','b']) returns NULL if either is NULL. DuckDB, Postgres and BigQuery would skip the NULL and return the other value.
  • sf_div0(a, b) returns 0 on a zero divisor. A hand-written a / nullif(b, 0) returns NULL — on exactly the rows anyone added the guard for.
  • sf_datediff(part, start, end) takes the part first. dbt-core's own datediff takes it last, so passing Snowflake's arguments through gives a sign-flipped answer in the wrong unit.
Corrected

Two numbers in my first survey were wrong

Building the detector properly disproved both. I had reported iff at 182 uses and dateadd at 27, from a substring grep.

iff does not appear in this project at all. The 182 was datediff( — which ends in the characters iff(. A word-boundary scan finds zero. And all 27 dateadd calls are {{ dbt.dateadd(...) }}, dbt's own cross-database macro, portable already.

So the conclusion is better than I first reported: this project has no unsupported functions. Its entire portability risk is the ambiguous set below — the half that runs without complaint.

Real risk

128 call sites resolve on DuckDB and can still be wrong

date_trunc ×66, datediff ×30, least ×27, greatest ×7, listagg ×5 — all raw SQL, all resolvable, none of them guaranteed to mean what the author meant. least and greatest disagree about NULLs; date_trunc and datediff disagree about argument order across dialects.

These are never translated automatically. pf dialect reports each with the macro that pins the source dialect's semantics, and a human confirms which warehouse the SQL was written for before wrapping. That confirmation is the actual work, and it cannot be skipped — the same text means different things depending on the answer.

The remaining 363 date_trunc and 153 datediff occurrences are already {{ dbt.* }} calls and are correctly ignored.

Trivial

The package dependencies are nearly vestigial

Three packages are declared. Actual usage across 1,058 models: dbt_utils 5 call sites (4 expression_is_true tests, 1 generate_surrogate_key), dbt_date 2 (both get_base_dates), dbt-audit-helper zero.

So: keep dbt_utils under the platform's existing >=1.3.0,<2.0.0 pin — 1.3.3 satisfies it. Drop audit-helper entirely, which is a bonus: it was pinned to git revision: main, i.e. unpinned, which the vendor policy would never accept. That leaves dbt_date as the only genuinely new dependency, for two call sites.

Nothing to do

No orchestrator to migrate, and no ingestion to port

The Airflow/Prefect→Dagster path doesn't apply — there is no Python in the repo at all. Dagster assets come from the platform's dagster-dbt factory once the project is registered. Source data is 59 static seed CSVs behind var('load_source_data'), not a pipeline.

Keep them as seeds. Writing dlt pipelines to load static fixture CSVs would be ceremony; add dlt when a real source appears. Note the platform will still expect src/jaffle_shop/ to exist, so scaffold it and leave it empty of sources.

Verified

No model name collisions

dbt's namespace is flat, so 1,058 models across 38 mart folders is a real collision risk. Checked: zero duplicate basenames. The tree can be flattened or restructured without renaming anything.

What is now built, and reusable

Every finding above came from a generic check, not a jaffle-specific one. Each is registry-driven or discovered at runtime, so the next import gets the same scrutiny without anyone editing code.

dbt-snowflake toolkit Adapter-dispatched, so it covers DuckDB, Postgres, Redshift, ClickHouse, BigQuery and Snowflake. A BigQuery-origin project gets a bq_* sibling — added to one tuple and one macro-paths entry.

path keys Reads test-paths, snapshot-paths and analysis-paths from the source rather than assuming dbt's defaults, then normalises into this platform's layout. This is what found jaffle's 3 tests, 2 snapshots and 3 analyses — all previously dropped in silence.
config re-keying The source's per-directory config follows its models through the layer mapping, so bronze: becomes staging: and two layers collapsing onto one merge. Without it every tag and materialisation is silently lost.
card rollup Any section over its limit is summarised by tag namespace — domain, then type, then criticality — instead of truncated to a count. Falls back cleanly when a project has no tags, and refuses to "group" into a single bucket.
scale guard Reports density rather than budget, and says whether the project carries tags the card can roll up by. Kept in step with the card's own section limit by a test, so the advice cannot drift from the behaviour.
package audit Counts real call sites per package and flags git pins on a moving branch. Found audit-helper at zero uses and unpinned.

pf onboard refuses to apply while any blocking finding stands, unless you pass --force. 73 tests cover it, including every toolkit macro compiled through dbt against a real adapter.

The plan

Five phases. Each has an exit criterion that is checkable, not a judgement call — the point is that you can tell whether a phase is actually finished.

PHASE 1

Clear the platform-tier decisions

Nothing else can start. All three are edits to shared infra, so they happen while not in a project session.

  • Decide the ontology question — extend v2 with retail and supply-chain concepts, or scope the import to what fits.
  • Restore the context generator, or stop committing its output — TOOLKITS.md and seven tools_card.md files are checked in here without the code that produces them.

Everything else in this phase is done: pf onboard, pf dialect, the macro toolkit and the card rollup are all on this branch, with 92 tests.

Exitpf ontology shows the agreed concept set; pf tokens still green on the seven existing projects.
PHASE 2

Scaffold and land the code

Mechanical, and the fast part. Survey first, apply second.

uv run pf new-group jaffle
uv run pf new-project jaffle jaffle-shop --with evidence,github
uv run pf onboard jaffle jaffle-shop \
  https://github.com/DataRecce/jaffle-shop-expand   # plan
uv run pf onboard jaffle jaffle-shop <src> --apply

The config merge, the reserved-macro exclusion and the toolkit wiring all happen in the apply. What is left by hand: drop audit-helper, add dbt_date and its dbt_date:time_zone var, then work the pf dialect report — confirm the source dialect, and wrap the 128 ambiguous call sites in their sf_* macros.

Exitpf dialect clean; dbt deps, dbt seed --vars 'load_source_data: true' and dbt build all green on DuckDB — 1,058 models and ~794 tests passing.
PHASE 3

Make it legible to the platform

This is where the real cost sits, and it is annotation work no tool can infer. Write contracts/annotations.yaml for the raw tables in scope — concept, roles, renames, FK links, grain and description per resource.

Start with the 6 ecom tables. They are the original jaffle core, they carry the semantic models and metrics, and they are the only ones with a genuine business shape. The other five domains are synthetic; decide domain by domain whether they earn annotations or stay unannotated mass.

Be aware of the trap: validate_project only warns on missing annotations. The project will pass pf check while contributing nothing to the graph, the metrics or the gate. Passing is not the same as onboarded.

ExitEvery in-scope resource resolves to a concept; pf kg build produces a graph with real edges; pf tokens green with the summarised card.
PHASE 4

Wire the platform's machinery

  • pf dagster-workspace to register the code location; assets come from the dagster-dbt factory.
  • Evidence reporting from the semantic layer — the 6 existing semantic models and 3 metric files are a real head start.
  • The GitHub impact gate on PRs. Expect pf impact blast radius to be large and slow here; measure it before trusting it in CI.
  • Settle the maxFiles question — my recommendation is to exclude this project from loops rather than raise the cap.
Exitpf check clean; the project appears in pf status; a test PR touching one mart produces a correct, bounded impact report.
PHASE 5

Snowflake

Only once DuckDB is green, per your call. Add a snowflake output to the project's profiles.yml from your credentials. The sf_* macros dispatch on the adapter, so they compile to native Snowflake functions with nothing to switch off.

Because the models were made portable rather than rewritten, this is a connection change and a full build — not a migration. Compare row counts per model between the two targets; that diff is the actual proof the macros were faithful, and it is the only proof that counts.

What no tool can do for you

Everything above that a command can perform, a command performs. This is the residue — the judgement that decides whether the project is genuinely part of the platform or merely stored in it.

  • Which of the six domains deserve ontology concepts, and which stay unannotated fixture mass.
  • The grain of each mart — 772 of them, and meta.grain is what makes the impact gate meaningful rather than decorative.
  • Which foreign keys are real relationships versus incidental shared column names.
  • Whether raw_items is a first-class concept (OrderLine) or a grain of Order — this shapes every downstream fact table.
  • Which of the 38 mart folders are business outputs and which are synthetic shape-tests that should never reach a dashboard.
  • Whether the 3 existing metric definitions are correct under this platform's semantics, particularly any ratio metric — those must re-divide as sum(num)/sum(den), never avg(ratio).

Method. Every number came from a shallow clone surveyed on 14 Aug 2026, then re-derived by the tooling described above rather than by grep. That re-derivation is what corrected the iff and dateadd figures, and what raised date_trunc from a portable footnote to the main finding.

On catalogue lookups. duckdb_functions() is authoritative when a name is present and unreliable when it is absent: coalesce, percentile_cont and grouping all work and none of them appear in it. The detector therefore layers three sources — the catalogue, an allowlist for parser-level forms and ordered-set aggregates, and a binder probe that separates "no such function" from "wrong arguments". A single-source lookup reports problems that do not exist, which is how a tool teaches people to ignore it.
